Introduction

jrs is a build system for the JVM, written in Rust. It builds, tests, runs and packages a single-module Java project from one jrs.toml manifest, resolving dependencies from Maven Central. Kotlin, Scala and Groovy compile alongside Java.

It aims for the ergonomics of Cargo: a small declarative manifest, a committed lockfile, one binary, and no build script to write. A project that holds nothing but src/ and jrs.toml can be cloned and started with jrs run: its dependencies are downloaded and linked, and no JDK flag is typed by hand.

A driver, not a compiler

jrs does not reimplement the JDK. It shells out to javac, java and jar, and for the features that need them to javadoc, jdeps, jlink, jpackage and GraalVM's native-image. The Kotlin, Scala and Groovy compilers, the JUnit launcher, JaCoCo and ProGuard are resolved from Maven Central like any library, pinned in the lockfile, and run on your JDK. Toolchain output is passed through verbatim, so a javac error looks exactly like a javac error. 

jrs.toml ──parse──► manifest ──► resolve ──► jrs.lock ──► classpath
                                                              │
 src/ + classpath ──► compile ──► target/classes ──► test | run | package

What jrs deliberately does not do

  • No plugin system and no build DSL. Configuration is declarative TOML. A project's own build steps are tasks: subprocesses jrs runs at fixed points, which can extend the build but never replace, remove or reorder its phases. No user code runs inside jrs.
  • No multi-module builds. One manifest is one module; there is no reactor.
  • No publishing to a repository (deploy / publish).
  • No Android, no JPMS module-descriptor configuration, no annotation-processor path (processors still work from the classpath, see Annotation processors), and no IDE project files.
  • For Kotlin, Scala and Groovy: nothing off the JVM (Multiplatform, JS, Native), no compiler plugins, no kapt or KSP.
  • No building from pom.xml or build.gradle. They are read once, by jrs migrate, and never treated as a build input.

Status

Experimental

jrs is experimental and is not a replacement for Maven or Gradle: it implements a deliberately narrow subset of what they do. Evaluate it against your own requirements before adopting it for production builds. The roadmap lists the known gaps, and the design specification explains the reasoning behind every behaviour described here.

Installation

jrs is a single self-contained binary. Install it with the script, download a release by hand, or build it from source.

Requirements

  • A JDK 17 or newer on PATH, or pointed at by JAVA_HOME. jrs does not bundle a compiler. A project can also pin a JDK version that jrs then finds among the JDKs installed on the machine.
  • Nothing else. The Kotlin, Scala and Groovy compilers are downloaded from Maven Central when a project turns them on.
  • Building jrs itself from source needs a Rust toolchain with edition 2024 support; the prebuilt binaries do not.

Install script (macOS and Linux)

curl -fsSL https://getjrs.dev/install.sh | sh

The script picks the build for your OS and CPU, checks it against the release's SHA256SUMS, and installs jrs into ~/.local/bin, which must be on your PATH. To install a particular release, or into another directory, pass options after sh -s --: 

curl -fsSL https://getjrs.dev/install.sh | sh -s -- --version 0.5.0 --to ~/bin

The same two settings can come from the environment as JRS_INSTALL_VERSION and JRS_INSTALL_DIR. The script is website/install.sh in the repository, if you want to read it before piping it into a shell.

Windows

In PowerShell:

curl.exe -fsSLO https://github.com/pwittchen/jrs/releases/latest/download/jrs-x86_64-pc-windows-msvc.zip
tar -xf jrs-x86_64-pc-windows-msvc.zip jrs.exe

then move jrs.exe to a directory on your PATH.

From source

git clone https://github.com/pwittchen/jrs.git
cd jrs
cargo install --path .

This places the jrs binary in ~/.cargo/bin.

Checking the installation

jrs --version
jrs --help            # every command
jrs build --help      # one command's flags

To get tab completion for commands and flags, see jrs completions.

Upgrading

Run the install script again for the latest release, or download the new archive by hand. A project that needs a newer jrs than the one installed says so itself when it declares jrs-version.

Uninstalling

Delete the binary: rm ~/.local/bin/jrs for a prebuilt one, or cargo uninstall jrs if it was built from source.

That leaves the downloaded dependencies behind. To reclaim that space, delete the dependency cache as well, for example rm -rf ~/Library/Caches/jrs on macOS, or whatever JRS_CACHE_DIR points at. Each project's target/ is disposable: remove it with jrs clean first, or delete it by hand afterwards.

Quick start

Create a project

mkdir hello && cd hello
jrs init

jrs init scaffolds jrs.toml, a starter main class and its test, in the current directory or in the path you give it. The project is named after its directory unless you pass --name. The templates declare JUnit 5 as a dev-dependency, so the first build downloads it.

CommandScaffolds
jrs initA Java application: a main class and a JUnit 5 test.
jrs init --libA Java library: no main class, a starter class and its test.
jrs init --lang kotlinThe same in Kotlin, with JUnit 5 tests.
jrs init --lang scalaThe same in Scala, with MUnit tests.
jrs init --lang groovyJava code, specified with Spock.
jrs init --checkAdds a check task that runs PMD over the Java sources after every compile. Refused with --lang kotlin and scala, whose starters have no Java sources.

Build, run and test

jrs build      # resolve dependencies, compile, copy resources
jrs run        # build, then run the main class
jrs test       # build, compile the tests, run them

The first build resolves the dependency graph, writes it to jrs.lock, and downloads the jars into the shared cache. Later builds read the lockfile and skip what is already up to date. Each phase prints one line, and a summary closes the run: 

    Resolving 1 declared dependency
  Downloading 6 artifacts
    Compiling hello v0.1.0 (1 source file)
     Finished build in 1.84s

  ┌─ jrs ─────────────────────────┐
  │  build   ok      1 class      │
  │  deps    6       6 downloaded │
  │  time    1.84s                │
  └───────────────────────────────┘

On a terminal the phases animate with spinners and live download bars. In CI, in a pipe or with --progress never, the same build prints only the plain lines. See Terminal output.

Add a dependency

jrs add com.google.guava:guava                 # newest release, into [dependencies]
jrs add org.assertj:assertj-core --dev         # test classpath only
jrs add org.postgresql:postgresql --runtime-only

jrs add edits jrs.toml in place, keeping its comments and order, and resolves again. You can equally edit the file by hand: jrs notices the change and re-resolves on the next build.

Package it

jrs package            # target/hello-<version>.jar, runnable with java -jar on this machine
jrs package --fat      # one self-contained jar that runs anywhere
java -jar target/hello-*.jar

Project layout

hello/
├── jrs.toml                  # the manifest
├── jrs.lock                  # generated by resolution; commit it
├── src/
│   ├── main/java/            # production sources
│   ├── main/kotlin/          # with [kotlin]; likewise scala/ and groovy/
│   ├── main/resources/       # copied into the jar
│   ├── test/java/            # test sources
│   └── test/resources/       # on the test classpath only
└── target/                   # generated; git-ignore it

Commit jrs.toml, jrs.lock and src/. Add target/ to .gitignore: everything in it is regenerated on demand. Every directory can be moved with a key in [project].

Starting from Maven or Gradle

jrs migrate --dry-run      # print the jrs.toml that would be written
jrs migrate                # write it; pom.xml / build.gradle stay untouched

See Migrating from Maven and Gradle for what carries over and what is reported for review.

Core concepts

A handful of ideas explain almost everything jrs does.

The manifest

jrs.toml at the project root is the only build configuration. It is declarative: what the project is, what it depends on, and how its JVMs and jars should be set up. Anything that belongs to a person or a machine (credentials, proxies, mirrors, JDK locations) lives in the user configuration instead, because the manifest is committed.

The lockfile

jrs.lock records every resolved artifact with its exact version and checksum, plus the graphs of the compilers and tools the project uses. You commit it, so every machine builds against the same jars. It is rewritten when jrs.toml changes or when you run jrs update. See jrs.lock.

The shared cache

Downloaded artifacts go into one cache per user, in the Maven repository layout, shared by every project. Downloads are checksum-verified and written atomically, so concurrent builds can share it safely. See Dependency cache.

The target directory

Everything a build writes goes under target/: classes, jars, reports, images, and jrs's own bookkeeping in target/.jrs/. Nothing there cannot be regenerated, so jrs clean can never lose your work. That is also why task-generated sources must live under it.

Three classpaths

ClasspathUsed byHolds
compilejavac for the main sourcesPlain and compile-only dependencies.
runtimejrs run, the jars and imagesPlain and runtime-only dependencies.
testCompiling and running the testsEverything: every kind of dependency, plus [dev-dependencies].

The order is deterministic: direct dependencies first, then transitive ones, each sorted by coordinate. jrs classpath prints any of them.

Compile units

The main sources and the test sources are two compile units. Each has one output directory (target/classes, target/test-classes) and one fingerprint, and is skipped when nothing it depends on changed. A unit mixes Java with at most one of Kotlin, Scala or Groovy. A Java-only unit recompiles file by file where it safely can. See Compilation and incremental builds.

Phases, hooks and tasks

Every command runs fixed phases in a fixed order: resolve, download, compile, copy resources, then test, run or package. Tasks are commands you declare; hooks attach them to fixed points between the phases. They extend the build without being able to reorder it.

Reproducible output

Directory walks are sorted, and jar entries are written sorted, with a fixed 1980 timestamp and fixed permissions. Two builds of the same inputs produce byte-identical jars.

jrs.toml at a glance

jrs.toml is a TOML file at the project root. Only [project] with a name and a version is required; every other table is optional. This one uses most of them: 

[project]
name = "my-app"
version = "1.0.0"
main-class = "com.example.Main"     # required for `jrs run` and fat jars

[java]
source = 21                          # -> javac --release 21
javac-args = ["-Xlint:all", "-Werror"]
jdk = 21                             # optional; build with JDK 21

[run]
jvm-args = ["-Xmx512m"]              # `java` flags for `jrs run`

[test]
jvm-args = ["-Dmode=test"]           # `java` flags for the test JVM

[kotlin]                             # optional: Kotlin alongside Java
version = "2.4.20"                   # the compiler, and the implied kotlin-stdlib

[managed]
# a version for wherever an artifact turns up in the graph
"com.fasterxml.jackson.core:jackson-databind" = "2.17.2"
# a BOM: its managed versions apply the same way
"org.springframework.boot:spring-boot-dependencies" = { version = "3.3.4", bom = true }

[dependencies]
"com.google.guava:guava" = "33.0.0-jre"                       # short form
"org.springframework.boot:spring-boot-starter-web" = {}       # versioned by [managed]
"jakarta.servlet:jakarta.servlet-api" = { version = "6.0.0", compile-only = true }
"org.postgresql:postgresql" = { version = "42.7.3", runtime-only = true }
"io.netty:netty-handler" = { version = "4.1.100.Final", exclusions = ["io.netty:netty-codec"] }
"org.lwjgl:lwjgl:natives-linux" = "3.3.3"                      # a classifier in the key

[dev-dependencies]                   # test classpath only

[repositories]                       # Maven Central is implicit and always last

Validation

A manifest error names the offending key and, where the TOML parser knows it, the line and column, and exits with code 2. An unknown key is a warning, not an error, so a manifest written for a newer jrs still builds on an older one where it can.

Requiring a jrs version

Forward compatibility has a limit: a jrs that ignores a key it does not understand may build a newer manifest wrongly. jrs-version in [project], like Cargo's rust-version, names the oldest jrs that may build the project: 

[project]
name = "my-app"
version = "1.0.0"
jrs-version = "0.5"          # or "0.5.1"

It is checked before any other key is read. An older jrs stops with exit code 2, naming the version the project needs, its own version, and where to download releases. A pre-release suffix on the running version is ignored (0.9.0-dev satisfies 0.9). jrs init and jrs migrate do not write the key.

Where jrs finds the manifest

jrs looks for jrs.toml in the working directory and then in each parent directory, so any command works from anywhere inside the project. --manifest-path points at a manifest elsewhere, either the file itself or the directory holding it: 

jrs --manifest-path ../other-project build
jrs --manifest-path /work/api/jrs.toml test

[dependencies] and [dev-dependencies]

Each entry maps a quoted "group:artifact" coordinate to a version. [dependencies] are what the main code needs; [dev-dependencies] are on the test classpath only and never packaged. 

[dependencies]

[dev-dependencies]

"org.assertj:assertj-core" = "3.26.0"

"io.netty:netty-transport-native-epoll" = { version = "4.1.100.Final", classifier = "linux-x86_64" }

Exclusions

A dependency's transitive graph stops at anything its exclusions match. Either half of a pattern can be *: "commons-logging:*" drops every artifact of that group, "*:*" keeps the dependency but none of what it brings. Exclusions declared in the libraries' own POMs are honoured as well.

compile-only

The dependency, and everything only it brings in, is on the compile and test classpaths, but not on the runtime one. It stays out of jrs run, the thin jar's Class-Path, lib/ and the fat jar. Use it for APIs the runtime environment provides (a servlet container), and for annotation processors such as Lombok.

runtime-only

The reverse: the dependency, and everything only it brings in, is on the runtime and test classpaths, but not on the one the main sources compile against. JDBC drivers, SLF4J bindings and Logback belong here, so code cannot accidentally depend on an implementation. It is in jrs run, the thin jar's Class-Path, lib/, the fat jar and runtime images. The tests compile against it too, as they do in Maven.

Classifiers

A classifier selects a jar published beside the main one, described by the same POM. It is part of the artifact's identity, so writing it in the key lets one table hold the same artifact with and without it: 

[dependencies]
"org.lwjgl:lwjgl" = "3.3.3"
"org.lwjgl:lwjgl:natives-linux" = "3.3.3"
"org.lwjgl:lwjgl:natives-macos-arm64" = "3.3.3"

Test dependencies

[dev-dependencies] take the same forms without compile-only or runtime-only. Declaring the test framework here is also how jrs test knows what to run: see Testing.

SNAPSHOT versions

A version ending in -SNAPSHOT resolves through the repository's maven-metadata.xml to its current timestamped build. Since a snapshot is republished under one name by design, its checksum is not pinned in jrs.lock. A cached snapshot is re-checked once a day, or on every build when it came from a file:// repository such as ~/.m2/repository; jrs update re-checks every snapshot at once. If the repository cannot be reached, the cached copy is used with a warning. Identical bytes are not rewritten, so a check that finds nothing new does not cause a recompile.

Local jars

A jar that is in no repository, such as a vendor's JDBC driver or a licensed SDK checked into libs/, is named by its path instead: 

[dependencies]
ojdbc = { path = "libs/ojdbc11.jar" }
vendor-api = { path = "libs/vendor-api.jar", compile-only = true }

[dev-dependencies]
fixtures = { path = "libs/test-fixtures.jar" }
  • The key is a name of your choosing (letters, digits, ., - and _), since the jar has no coordinate. The path is relative to the project root.
  • The jar is taken as it is, with no transitive graph. compile-only and runtime-only apply as usual.
  • jrs.lock records the relative path and pins the jar's SHA-256. The jar is re-hashed on every build, and one that changed under the same name fails the build until jrs update pins it again. A missing jar is an error naming its path.
  • jrs tree shows it as ojdbc = libs/ojdbc11.jar, jrs remove ojdbc removes it, and jrs outdated skips it.

Version ranges

Maven version ranges such as [1.0,2.0) are rejected with a clear error rather than guessed at. jrs only builds against versions written down.

[managed] and BOMs

[managed] keeps versions in one place. It does what Maven's <dependencyManagement> and Gradle's platform() and constraints { } do: 

[managed]
"org.springframework.boot:spring-boot-dependencies" = { version = "4.1.1", bom = true }
"com.fasterxml.jackson.core:jackson-databind" = "2.19.0"

[dependencies]
"org.springframework.boot:spring-boot-starter-webmvc" = {}   # versioned by the BOM
"com.fasterxml.jackson.core:jackson-databind" = {}           # versioned by [managed]
  • A managed version holds an artifact to that version wherever the graph reaches it, ahead of nearest-wins mediation. It adds nothing to a classpath: an artifact nothing depends on stays out.
  • bom = true imports a BOM's own managed versions instead of managing the BOM itself.
  • A dependency may leave its version out, as {} or as a long form without version, and takes it from [managed]. Upgrading the BOM then upgrades it.
  • A version written in [dependencies] still wins for that dependency, as it does in Maven.
  • Order matters: the table's own entries come before any BOM's, and an earlier BOM before a later one. A managed version covers every classifier of its group:artifact.

jrs tree marks a version that [managed] decided with (managed), jrs outdated checks every entry, BOMs included, and jrs add leaves the version out of what [managed] covers. A manifest without the table keeps its lockfile byte for byte.

[repositories]

Additional Maven repositories, tried in declaration order. Maven Central is implicit and always tried last. 

[repositories]
internal = "https://repo.example.com/maven2"
local-m2 = "file:///home/me/.m2/repository"

Confining a repository to its groups

The long form names the groups a repository serves:

[repositories]
internal = { url = "https://nexus.example.com/maven", groups = ["com.acme", "com.acme.*"] }
jitpack = { url = "https://jitpack.io", groups = ["com.github.someone"] }
  • com.acme is that group; com.acme.* is every group below it.
  • A repository with groups is asked only for those groups.
  • A group that some repository's groups names is looked up only there, never in another repository or in Maven Central.

That keeps a public repository from answering for your internal groups (dependency confusion), and saves a request per artifact to repositories that cannot have it.

Credentials and mirrors

jrs.toml is committed, so credentials never go in it. They live in the user configuration, or in JRS_REPO_<NAME>_* environment variables, keyed by the repository's name. Mirrors are set there too, and work for Maven Central as for any other repository.

Java agents

Agents are named by coordinate, never by path: jrs.toml is committed and the jar lives in the machine's cache.

  • group:artifact is looked up in the resolved graph, so it is the version jrs.lock pins, and it has to be a dependency. run.java-agents looks on the runtime classpath. An agent the graph does not hold is a manifest error that says where to declare it.
  • group:artifact:version (a classifier may follow) is for an agent the program never calls, such as OpenTelemetry's. jrs resolves that one jar alone, as it does a compiler, pins it in jrs.lock as a [[tool]] named run.java-agents.<group>:<artifact>, and keeps it off every classpath.

Agents go to the JVM ahead of every other argument. run.java-agents also goes into the launchers of --jlink, --jpackage and --dist, which load an agent from the graph from their lib/ and a pinned one from their agents/. An image or distribution of a --fat jar can carry only pinned agents, since the fat jar has unpacked the others, and jrs says so.

jrs.lock

Resolution writes jrs.lock beside the manifest. It records every resolved artifact with its exact version and checksum, so builds are reproducible and can run offline. Commit it. 

version = 1
manifest-checksum = "sha256:17e5005c…"
roots = ["com.google.guava:guava", "org.apache.commons:commons-lang3"]
test-roots = ["org.junit.jupiter:junit-jupiter"]

[[package]]
group = "com.google.guava"
artifact = "guava"
version = "33.3.1-jre"
classpath = "compile"
packaging = "jar"
depth = 1
direct = true
checksum = "sha1:…"

When it is rewritten

  • When jrs.toml changes in a way that affects resolution. manifest-checksum covers the dependencies, repositories, [managed], each language's version and each task's dependencies; when it no longer matches, the next build resolves afresh. Adding a task or changing a flag does not.
  • When you run jrs update, which also re-checks every snapshot and re-pins local jars.

Otherwise the lockfile is read, not rewritten, and resolution costs a few milliseconds. After a merge conflict in jrs.lock, keep either side and run jrs update.

Checksums are pins

A jar downloaded while the lockfile is in use must match its recorded checksum as well as the repository's own .sha1, or the download is discarded and the build fails. A repository that starts serving different bytes under the same version cannot slip them in. A -SNAPSHOT is recorded without a checksum.

What it contains

BlockHolds
[[package]]One per artifact: group, artifact, version, its classpath (compile, provided, runtime or test), packaging, depth in the graph, whether it is direct, its checksum, and managed = true when [managed] decided its version.
[[tool]]A graph that never meets the project's: a compiler (kotlin-compiler, scala-compiler, groovy-compiler), the obfuscator, a task's tools (tasks.<name>) or a pinned agent. It has a name, its roots, and [[tool.package]] entries in the same format.
[[local]]A local jar: its name, its path relative to the root, its classpath and a sha256.

The file says version = 2 only when it has [[tool]] blocks, so a plain Java project's lockfile stays byte-identical across jrs releases. It never records an absolute path: cache locations are recomputed on every machine.

Dependency resolution

Resolution turns the declared coordinates into one flat, deduplicated set of jars. It runs when there is no lockfile, when the manifest changed, or on jrs update; otherwise the lockfile answers.

The algorithm

  1. Start from the manifest's direct dependencies.
  2. Fetch each POM (cache first) and parse it: interpolate ${…} properties, walk <parent> chains, and fill in missing versions from <dependencyManagement>. Then apply [managed].
  3. Collect the POM's compile and runtime dependencies. provided, system and test ones are skipped, and so is anything marked <optional>true</optional>. Exclusions, the POM's and the manifest's, cut the graph.
  4. Repeat for everything new, breadth-first, level by level, with each level's fetches in parallel.
  5. Mediate conflicts, assign each jar its classpath, and write jrs.lock.

A <type> of jar, bundle, ejb or maven-plugin is a jar; test-jar is the jar classified tests; pom contributes dependencies but no jar; anything else is skipped with a warning. Cycles in the graph terminate.

Nearest wins

When two paths ask for different versions of one artifact, the version nearest the root wins, as in Maven. Ties at the same depth go to the dependency declared first in the manifest, and jrs warns, naming both versions. So a version you declare directly always wins, and to force a transitive version you either declare the artifact yourself or manage it: 

[managed]
"com.fasterxml.jackson.core:jackson-databind" = "2.19.0"   # wherever it appears

[managed] is settled before mediation: every path to a managed artifact asks for the same version, so there is nothing to mediate.

Inspecting the graph

jrs tree                                  # everything
jrs tree --depth 1                        # what you declared
jrs tree --why org.checkerframework:checker-qual   # who brings this in?

Where artifacts come from

Repositories are asked in declaration order, Maven Central last, except where a repository's groups claims a group. A 404 moves on to the next repository; a 401 or 403 fails at once and says where credentials go. A dropped connection or an HTTP 429 or 5xx is retried, with a doubling backoff, up to three attempts in total. Mirrors and proxies from the user configuration apply to every request.

Compilation and incremental builds

jrs's rule is that skipping work must never produce a wrong result: a spurious recompile costs seconds, a stale class costs a wrong answer. When in doubt, it compiles.

When a unit is fresh

Each unit, main and test, has a fingerprint of its settings (flags, source list, classpath, including each jar's size and modification time) and its sources. A source counts as changed when its contents did: one whose size or mtime moved is hashed and compared, so merely touching a file does not rebuild. A fresh unit prints Fresh and costs a staleness check.

File by file

A Java-only unit compiles only what a change needs. Every build records in target/.jrs/<unit>.index which classes each source produced, their API, their constants and which classes of the unit they refer to. Then:

  • A change inside method bodies compiles that one source.
  • A change to a class's API also compiles every source that refers to it, transitively, since a subclass passes an inherited change on to its own users.
  • The classes are the ones a whole build would have written, byte for byte.

The whole unit is compiled instead, into an emptied output directory, when file by file cannot be sure:

  • the settings changed, or there is no index yet;
  • a source was added or deleted, or a top-level class appeared or disappeared;
  • a compile-time constant changed, since javac inlines constants without a reference back;
  • annotation processors or javac plugins are in play, or there is a module-info.java;
  • the unit has Kotlin, Scala or Groovy sources.

Emptying the directory means a class whose source was deleted or renamed can never survive into the jar.

Compile avoidance for tests

The test unit depends on the main classes' API, not their bytes: class flags, supertypes, and every non-private member's signature, annotations and constant values. A main change that leaves that API alone, such as a fix inside a method, leaves the tests fresh. Kotlin and Scala classes count by their bytes (inline functions and macros carry bodies across), and so does every class once the main code registers an annotation processor or Groovy AST transformation.

Resources

src/main/resources is copied into target/classes and src/test/resources into target/test-classes, skipping files whose size and mtime match. A resource you delete is deleted from the output too. jrs records what it copied and only ever removes those files, never a class or a processor's output.

Seeing what happened

jrs -v build            # every command line, and how many sources each unit compiled
jrs build --timings     # how long each step took

Watch mode

jrs build --watch
jrs test --watch
jrs test --watch --filter '.*Parser.*'
jrs task generate --watch

Watch mode runs the command, then polls every 300 ms for changes to the manifest, every source and resource root of every language, and every task's inputs. Once a change has settled, it runs the command again. The manifest is re-read on every run, so editing jrs.toml takes effect immediately.

A failure is reported and waited out rather than ending the loop, since the next save is usually the fix. Nothing under the target directory is watched, so a generator's output can never retrigger it. Stop with Ctrl C.

jrs test runs the JUnit Platform console launcher, which jrs resolves itself, over target/test-classes. You only declare the test framework.

Choosing what runs

jrs test --filter '.*Integration.*'                    # classes by regex

Reports

JUnit XML lands in target/test-reports, where CI systems look for it. Every run that leaves XML also gets target/test-reports/index.html: a static page with a row per class, failing classes first and unfolded with their stack traces. It is written for failing runs too, and jrs test prints its path. While the tests run, a live counter shows passed and failed tests.

Rerunning failures

--rerun-failed runs only what failed last time, read from the last run's XML: a plain method by name, one invocation of a parameterised test or a dynamic test by its JUnit unique ID, and otherwise the class. When nothing failed it says so and exits 0; with no earlier run at all it exits 2.

Retries and flaky tests

[test] retries = n, or --retries n, runs failing tests again up to n times, each attempt writing its XML into target/test-reports/retry-<n>/. A test that passes on a retry does not fail the run, but it is not counted as passed either: it is reported as flaky, by name and in the Finished line, and marked on the HTML page.

Fail fast

--fail-fast stops at the first failing test. On JUnit 6 it uses the launcher's own --fail-fast. The 1.x launchers of JUnit 5 and 4 do not have one, so jrs follows the launcher's test feed and stops it after the first failure; that run writes no XML. Launchers older than 1.10 (JUnit 5.9 and earlier) cannot be followed that way and run every test. A run stopped early is not retried.

Parallel test JVMs

[test] forks = n, or --forks n, splits the test classes among n JVMs running at once, like Gradle's maxParallelForks. Each JVM gets every n-th class in name order, so --filter and tags still apply. Their output is printed whole, one after another, once all finish; their XML lands side by side as TEST-<engine>-fork-<k>.xml. Retries, --rerun-failed, --method, --fail-fast and --debug run in one JVM. Tests that share a port, a database or a file must be ready for another JVM beside them.

Jupiter's own parallelism inside each JVM is switched on through jvm-args, or the same keys in src/test/resources/junit-platform.properties:

[test]
jvm-args = [
  "-Djunit.jupiter.execution.parallel.enabled=true",
  "-Djunit.jupiter.execution.parallel.mode.default=concurrent",
]

Coverage

jrs test --coverage

Records coverage with JaCoCo and writes an HTML report plus jacoco.xml to target/coverage. [test] jacoco-version picks the JaCoCo release. [test] coverage-minimum makes the run exit 1 when a project-wide total falls short, naming the counter and the minimum:

Debugging a test

jrs test --debug --method com.example.CartTest#addsItems

Running and debugging

jrs run builds and runs project.main-class on the runtime classpath, directly from target/classes; no jar is written.

Packaging

jrs package always writes target/<name>-<version>.jar. What differs is where the dependencies go.

Thin, portable or fat

CommandDependenciesRuns
jrs packageReferenced by the jar's Class-Path, in the local cache.With java -jar on the machine that built it.
jrs package --portableCopied into target/lib/, which the Class-Path points at.Anywhere the jar and its lib/ are shipped together.
jrs package --fatUnpacked into the jar itself.Anywhere, as a single file.

Only runtime dependencies are packaged: compile-only and [dev-dependencies] never are, runtime-only ones always are. A main-class becomes the jar's Main-Class.

Byte-identical jars

Entries are written in sorted order, with a fixed 1980 timestamp and fixed permissions. Two builds of the same inputs produce the same bytes, so a jar's checksum means something and caches downstream stay warm.

How a fat jar merges

Several jars often register the same file. A fat jar merges them instead of letting one copy overwrite the others, which would break things silently:

  • META-INF/services/* files are concatenated, so every ServiceLoader provider survives.
  • Groovy extension modules are merged.
  • Spring's spring.factories is merged key by key, META-INF/spring/*.imports as a union of lines, and spring.handlers, spring.schemas and spring.tooling are concatenated, so no auto-configuration is lost.

The project's own copy always comes first. A duplicate class is reported by name, with both jars; exclude one side, or relocate it.

Relocating packages

[package.relocate] moves packages inside a fat jar, as Maven Shade does, so it can carry a private copy of a library: 

[package.relocate]
"com.google.common" = "com.example.shaded.guava"
"org.slf4j" = { to = "com.example.shaded.slf4j", exclude = ["org.slf4j.impl.*"] }
  • jrs package --fat renames the package and every package under it, moves its classes and resources, and rewrites every reference: in your classes, in every dependency's, in META-INF/services/ files and in Spring's registries.
  • exclude keeps classes, or packages written <package>.*, where they are.
  • Only the fat jar is relocated. jrs run, jrs test and the thin and portable jars use the dependencies as they are; jrs package without --fat warns that the table does not apply.
  • jrs rewrites the names in each class's constant pool and nothing else, so no tool is downloaded. A class name inside a longer string, or in another kind of resource, is left alone. A class that cannot be read fails the build rather than ship unrelocated.

Manifest attributes

[package.manifest]
Implementation-Title = "{project.name}"
Implementation-Version = "{project.version}"
Automatic-Module-Name = "com.example.app"

Written after jrs's own attributes, in declaration order, in every kind of jar. See [package] for the rules.

Sources and Javadoc jars

jrs package --sources --javadoc

--sources writes target/<name>-<version>-sources.jar from the main sources, generated ones included. --javadoc runs jrs doc and jars target/doc into -javadoc.jar. They are the jars an IDE or a repository wants beside the main one, and they combine with every other flag.

After packaging

The post-package hook runs once the jar, and any image, is written. Its tasks see the jar as {jar} and $JRS_JAR: sign it, checksum it, upload it.

Obfuscation

[obfuscate]
version = "7.6.1"
keep = ["com.example.plugin.Api"]
proguard-args = ["-dontwarn org.foo.**"]
jrs package --fat --obfuscate

--obfuscate runs ProGuard over the jar just written, renaming classes, methods and fields and stripping debug information while leaving behaviour untouched: the same entry point runs and the same tests pass against the obfuscated jar.

  • ProGuard is resolved from Maven Central as its own tool graph, pinned in jrs.lock and run on the project's JDK, exactly like the compilers. jrs tree --tool obfuscator shows it.
  • The entry point and every META-INF/services/ provider keep their names, so reflection through them and ServiceLoader still work. keep adds any other names a framework looks up; proguard-args passes anything else to ProGuard.
  • It runs after packaging, so it composes with the fat-jar merge rules rather than redoing them. Pair it with --fat for a self-contained obfuscated jar.
  • It is opt-in: without the flag, jrs package is unaffected by the table.

Kotlin, Scala and Groovy

A [kotlin], [scala] or [groovy] table compiles that language alongside Java:

[kotlin]
version = "2.4.20"
src/main/kotlin/com/example/Main.kt      # fun main() at file level: main-class = "com.example.MainKt"
src/main/java/com/example/Legacy.java    # may use the Kotlin classes, as they may use it
src/test/kotlin/com/example/MainTest.kt

The compiler is jrs's dependency, not yours

It is resolved from Maven Central as a graph of its own, pinned in jrs.lock beside yours, and run on the project's JDK. Its dependencies never mediate against the project's: the Kotlin compiler's own coroutines cannot change yours. jrs tree --tool kotlin-compiler shows its graph and jrs outdated lists newer releases. Supported: Kotlin 2.0+, Scala 2.13.9+ and 3.3+, Groovy 4.0+.

The runtime library is implied

kotlin-stdlib, scala-library / scala3-library_3, or groovy is added at the compiler's version. You don't declare it; if you do, your declaration wins. Groovy declared under [dev-dependencies] stays off the runtime classpath and out of the jar, which is what a project with only Spock tests wants.

Mixed sources, both ways

Kotlin and Scala compile first, reading the Java sources for their symbols, then javac compiles the Java against their classes. Groovy compiles both itself, jointly. A compile unit mixes Java with at most one other language, but main and test are separate units, so Kotlin code with Spock tests is fine. A .kt file without a [kotlin] table is an error, not a file silently skipped.

One release for everything

java.source, or the JDK's version, is passed to every compiler, so a jar never mixes bytecode levels. A compiler that does not know the release fails with its own message, and jrs adds a one-line hint.

Kotlin specifics

  • Kotlin tests see the main code's internal declarations.
  • A file-level main in Main.kt compiles to MainKt; jrs run says so when main-class names Main.
  • A Multiplatform library whose root artifact does not resolve to classes needs its -jvm artifact declared instead, such as kotlinx-coroutines-core-jvm.

Not supported

Compiler plugins (Kotlin's allopen, spring, serialization), kapt and KSP, Kotlin Multiplatform projects, Dokka, and incremental compilation or daemons for these languages. Units with them are compiled whole.

Tasks and hooks

A task is a command jrs runs for you: a code generator before javac, a checksum after the jar, a formatter on demand. Tasks are subprocesses; [hooks] attaches them to fixed points of the build. 

[tasks.build-info]
description = "Generate BuildInfo.java"
script = "build/GenerateBuildInfo.java"
args = ["{target}/generated/sources", "{project.version}"]
inputs = ["build/GenerateBuildInfo.java"]
outputs = ["{target}/generated/sources"]
source-outputs = ["{target}/generated/sources"]

[tasks.checksum]
description = "Write a SHA-256 next to the jar"
shell = "shasum -a 256 \"$JRS_JAR\" > \"$JRS_JAR.sha256\""

[tasks.release]
description = "Package, then checksum"
depends-on = ["package", "checksum"]

[hooks]
pre-compile = ["build-info"]
post-package = ["checksum"]
jrs task release
jrs task --list

Actions

A task has exactly one action, or none:

  • run: a program and its arguments, passed to the OS without a shell, so it behaves the same everywhere. The program is looked up on PATH with the JDK's bin/ first (so java is the project's JDK), or taken relative to the root if it contains a path separator.
  • shell: a string for sh -c, or cmd /C on Windows. Pipes and redirects work, but it is not portable: the same string goes to a different shell on each platform.
  • script: a .java file run by the project's JDK in source-launcher mode, no compile step. The portable way to write build logic.
  • main: a class from the task's own dependencies, so a Java tool from Maven Central needs no installing.
  • none: the task only runs its depends-on, like release above.

args follow the action: appended to run, passed to the script or main class, and as $1, $2… to a shell string.

A generator in Java

import java.nio.file.Files;
import java.nio.file.Path;

public class GenerateBuildInfo {
    public static void main(String[] args) throws Exception {
        Path dir = Path.of(args[0], "com", "example");
        Files.createDirectories(dir);
        Files.writeString(dir.resolve("BuildInfo.java"), """
            package com.example;

            public final class BuildInfo {
                public static final String VERSION = "%s";
            }
            """.formatted(args[1]));
    }
}

Hooked into pre-compile, it writes a source under target/ that source-outputs adds to the main compile. With inputs and outputs declared, it only runs when the script changed.

Tools from Maven Central

[tasks.format]
description = "Format App.java in place"
main = "com.google.googlejavaformat.java.Main"
args = ["--replace", "src/main/java/com/example/App.java"]

[tasks.format.dependencies]
"com.google.googlejavaformat:google-java-format" = "1.22.0"

A task's dependencies take the [dependencies] forms, without compile-only, runtime-only, local jars or [managed] versions. They are resolved as a graph of the task's own that never meets the project's, pinned in jrs.lock as a [[tool]] named tasks.format, and shown by jrs tree --task format. They download with everything else on a fresh resolution, or when the task first runs. A script task can take dependencies too, as its classpath.

Checks: PMD, Checkstyle, SpotBugs

Checkers are tools like any other, so they need neither a plugin nor an install. jrs init --check scaffolds this one; a violation fails the build after PMD's report: 

[tasks.check]
description = "Check the Java sources with PMD's quickstart rules"
main = "net.sourceforge.pmd.cli.PmdCli"
args = ["check", "--no-progress", "--rulesets", "rulesets/java/quickstart.xml", "--dir", "src/main/java", "--cache", "{target}/pmd.cache"]

[tasks.check.dependencies]
"net.sourceforge.pmd:pmd-cli" = "7.27.0"
"net.sourceforge.pmd:pmd-java" = "7.27.0"

[hooks]

Hooks

HookRuns
pre-compileAfter dependencies are resolved, before the main sources are compiled. For code generation.
post-compileAfter the main classes and resources are in target/classes.
pre-testAfter the main build, before the test sources compile.
post-testAfter the tests, only if they passed.
post-packageAfter the jar, and any image, is written.

Commands include each other, so their hooks do too: build fires the compile hooks, and test, package and run add their own. doc fires pre-compile, since it documents generated sources. A hook runs every time its point is reached, whether or not javac had work to do.

Ordering

  • Tasks run one at a time, and each task and each built-in runs at most once per command. build in the depends-on of a task hooked into jrs test does not build twice.
  • depends-on runs depth-first in list order, dependencies before dependents; a hook's tasks run in the order it lists them.
  • A built-in in depends-on runs as its command would, hooks included, but without its summary. test runs unfiltered, and package builds the plain thin jar.
  • A cycle is a manifest error, named in full (a → b → a), including one through a built-in, such as a pre-compile task that depends on build.

Placeholders

run, args, cwd, env values, inputs, outputs and the *-outputs lists are expanded before the process starts. {{ and }} are literal braces. An unknown placeholder is a manifest error.

Up-to-date checks

Only a task with both inputs and outputs can be skipped. Entries are files or directories relative to the root, a directory meaning everything under it; there are no globs. The fingerprint covers the expanded command, args, cwd and env, the JDK version, each input's path, size and mtime, any classpath the task uses, and its tool jars. When it matches and every output exists, the task prints Fresh <name> (task) and does not run. A task without both always runs. jrs clean forgets every fingerprint.

Generated sources and resources

The source-outputs and resource-outputs of tasks reached from pre-compile feed the main unit and target/classes; those reached from pre-test feed the test unit. They must lie under the target directory, because jrs clean must never delete anything you wrote and watch mode must not retrigger on a generator's output. A project whose sources are all generated still builds.

How tasks run

  • The task named on jrs task <name> inherits the terminal and returns its exit code.
  • Tasks run by hooks or as dependencies have stdin closed and their output passed through to stderr, so stdout stays the command's own. One that fails stops the command with exit code 1, after its output.
  • -v echoes each expanded command, its working directory and its JRS_ variables.

Security

jrs build on a freshly cloned project runs whatever its [hooks] name, as gradle build or npm install would. Read a project's jrs.toml before building it if you do not trust it. tree, classpath, update, verify, outdated, add, remove, cache, init, migrate, completions and clean never run a task, so inspecting a project with them is always safe.

Annotation processors

jrs has no separate processor path; configuring one is a non-goal. But javac runs any processor it finds on the compile classpath, so Lombok, MapStruct, Dagger and the like work as compile-only dependencies: 

[java]
javac-args = ["-proc:full"]        # needed from JDK 23 on

[dependencies]
"org.projectlombok:lombok" = { version = "1.18.34", compile-only = true }
"org.mapstruct:mapstruct" = "1.5.5.Final"
"org.mapstruct:mapstruct-processor" = { version = "1.5.5.Final", compile-only = true }

Since JDK 23, javac only runs processors found on the classpath when given -proc:full. JDK 21 and 22 accept the flag and don't need it; JDK 17 rejects it, so leave it out there. jrs migrate translates annotationProcessor and <annotationProcessorPaths> into exactly this. A unit with processors is always compiled whole, since jrs cannot see what they generate.

Choosing the JDK

By default jrs builds with the JDK at JAVA_HOME, or failing that the javac on PATH. It needs JDK 17 or newer, and fails with an actionable message when the JDK is missing or older than java.source.

Pinning a version

A project can pin a JDK feature version instead, in the first of these that exists:

  1. jdk = 21 under [java] in jrs.toml;
  2. a .java-version file, as jenv, asdf and mise write (21, temurin-21.0.2);
  3. a .sdkmanrc file with a java=21.0.2-tem line.

It is a version, never a path, since the manifest is committed and a path belongs to one machine.

Where a pinned JDK is found

  1. The user configuration's [jdks] table.
  2. The JDK at JAVA_HOME or on PATH, if it is that version.
  3. The JDKs installed in the usual places: SDKMAN!, asdf, mise, IntelliJ and Gradle toolchain directories in your home; /Library/Java/JavaVirtualMachines, /usr/lib/jvm, /usr/java and /opt/java; Program Files on Windows; and the JAVA_HOME_<version>_<arch> variables actions/setup-java exports.

When several builds of that version are installed, the newest wins. If none is found, the error lists the versions that were. jrs -v build names the JDK it picked. 

[jdks]
21 = "/opt/jdks/temurin-21"
25 = "/opt/graalvm-25"

The other JDK tools

java, jar, javadoc, jdeps, jlink, jpackage and native-image are taken from beside the selected javac, and a JDK that lacks one is an error naming it. Tasks get the same JDK as JAVA_HOME, and the Kotlin, Scala and Groovy compilers run on it.

Dependency cache

Downloaded artifacts are stored in one Maven-layout cache per user, shared by every project:

PlatformLocation
macOS~/Library/Caches/jrs
Linux and other Unix$XDG_CACHE_HOME/jrs, else ~/.cache/jrs
Windows%LOCALAPPDATA%\jrs\cache

JRS_CACHE_DIR overrides it, which is useful in CI, where the cache is worth keeping between runs. jrs cache path prints the one in use.

Safe to share

Every download is verified against the repository's checksum and, when the lockfile pins it, against jrs.lock; a mismatch is deleted and fails loudly. Downloads go to a temporary file that is renamed into place, so an interrupted run never leaves a truncated jar, and concurrent builds can share one cache. Cached jars are not re-hashed on every build; jrs verify does that on demand.

Offline builds

--offline uses only the cache and the lockfile, and fails on anything missing rather than reaching the network. Run jrs fetch first to download everything a build and a test run need.

Pruning

jrs cache prune --dry-run             # what would go
jrs cache prune                       # drop what no project's jrs.lock names
jrs cache prune --unused-for 30       # drop what no build has used in 30 days

Every build records its lockfile in the cache, so a plain prune keeps exactly what those projects' lockfiles name, their pinned compilers and tools included. Lockfiles that no longer exist are forgotten, and one that cannot be read stops the prune rather than risk a guess. It also drops parent POMs, BOMs, test launchers and JaCoCo jars, which only a fresh resolution or a --coverage run needs and which are downloaded again when wanted. --unused-for goes by when each artifact was last used, recorded in its access time at most once a day, so it works even on filesystems mounted noatime.

User configuration

Settings that belong to a person or a machine rather than the project live in one file per user. Every setting is optional, and a missing file is not an error.

Credentials

A [credentials.<repo>] table, named after a repository in jrs.toml, sends HTTP basic auth (username + password) or a bearer token. The password-env and token-env variants read the secret from an environment variable instead of the file. Environment variables take precedence over the file: 

export JRS_REPO_INTERNAL_USERNAME=ci
export JRS_REPO_INTERNAL_PASSWORD=…
export JRS_REPO_MY_REPO_TOKEN=…          # for a repository named my-repo

<NAME> is the repository name upper-cased, with every other character turned into _. Credentials are sent only to the repository they are named for.

Mirrors

[mirrors] redirects a repository, Maven Central included, to another URL. The key * mirrors every repository that has no mirror of its own. A mirror changes where bytes come from, not what the project is, so it does not change jrs.lock. file:// repositories are never mirrored, and credentials still go by the repository's name.

Proxy

Without a [proxy] table, HTTPS_PROXY, HTTP_PROXY, ALL_PROXY and NO_PROXY from the environment apply.

JDKs and parallelism

[jdks] maps a Java feature version to a JDK home, for a pinned version installed where jrs does not look. jobs sets the default for --jobs.

Continuous integration

jrs needs no special mode for CI; a few habits make it fast and strict:

  • Commit jrs.lock, so CI builds exactly what you built.
  • Persist the cache between runs, keyed on the lockfile. Set JRS_CACHE_DIR if the default location is inconvenient.
  • Warm, then build offline: jrs fetch downloads everything, and --offline afterwards proves nothing else is reached for.
  • Output adapts by itself. Animation is off whenever CI, GITHUB_ACTIONS, GITLAB_CI, TRAVIS, CIRCLECI, BUILDKITE, TEAMCITY_VERSION or JENKINS_URL is set, or stderr is not a terminal.
  • Collect reports from target/test-reports (JUnit XML and index.html) and target/coverage.
  • Gate on coverage with [test] coverage-minimum and jrs test --coverage.
  • Keep timings: --timings writes target/.jrs/timings.txt even under -q.

Editors and tooling

jrs generates no IDE project files. Instead it answers questions a tool can ask:

  • jrs metadata prints the whole project model as JSON: source and resource roots per language, output directories, the three classpaths with each jar's coordinate, the JDK and release, the main class and the tasks. See jrs metadata.
  • jrs fetch --sources downloads each dependency's -sources.jar, which jrs metadata then lists, for go-to-definition into libraries.
  • jrs classpath prints a classpath for a tool that only needs that.
  • jrs completions gives your shell completion for commands and flags.

For an IDE without jrs support, point its project at the source roots and add the jars jrs classpath --test prints as libraries; or migrate the other way temporarily and keep jrs.toml as the source of truth.

Terminal output

On a terminal jrs animates: spinners, live download bars, a live test counter, and a framed summary. The animation is a presentation layer over a build that produces identical results without it, and it never costs time.

Phase lines

Every phase prints one Cargo-style line, the verb right-aligned in 12 columns:

    Resolving 14 dependencies
  Downloading guava-33.0.0-jre.jar
        Fresh build-info (task)
    Compiling my-app v1.0.0 (47 source files)
    Packaging target/my-app-1.0.0.jar
         Task checksum (post-package)
     Finished package in 2.31s

A task prints Task <name> with the hook that ran it, or Fresh <name> (task) when its check let it be skipped.

When it animates

--progress auto, the default, animates only when stderr is an interactive terminal and none of these holds: --quiet or --verbose is given, NO_COLOR is set, TERM=dumb, or a CI variable is set. Otherwise each phase prints plain lines, a log rather than a canvas. --progress always and never force it.

Colour and glyphs

--color auto|always|never controls styling; NO_COLOR is honoured. --charset auto|unicode|ascii picks the glyphs for spinners, bars and trees; every glyph has an ASCII twin, and auto probes the locale.

Compiler and test output

javac's and the test launcher's diagnostics are passed through verbatim, never reformatted. The live region is torn down before they print, so errors always land in a clean terminal, and lines are truncated to the terminal width so nothing half-drawn reaches your scrollback.

Spring Boot

A Spring Boot build as start.spring.io generates it migrates whole. The Boot plugin with io.spring.dependency-management, or Maven's spring-boot-starter-parent, becomes Boot's BOM in [managed], so the starters stay versionless. -parameters, which Boot compiles with, goes into javac-args, and the @SpringBootApplication class becomes the main class. jrs package --fat then builds a runnable flat jar with Spring's registries merged.

Gradle version variables

A version kept in a variable is written into each declaration that uses it: ext, def, the Kotlin DSL's val and extra, and gradle.properties, used as "g:a:$v", ${project.v}, ${property("v")} or map notation's version: v, in platforms, mavenBom, constraints { } and Boot's plugin. A review line names the variable, since the manifest no longer shows those versions moving together. Only a variable assigned once, to a literal, outside a conditional, is used; anything else is reported, never migrated without its version.

Maven profiles

jrs.toml is one fixed configuration, so a Maven build migrates as a plain mvn build runs it: the profiles that build activates (<activeByDefault> ones, or one waiting only on a property being unset, such as !skipDocs) are merged in first, the way Maven merges them, and the others are listed with what activates them.

What needs rewriting by hand

  • Gradle tasks with a doLast { } closure, of another type such as Copy, or with a value built from a variable: listed with the reason, to rewrite as a run, shell or script task.
  • A -javaagent: in jvmArgs, a path into Gradle's cache, except Mockito's own recipe, which becomes test.java-agents = ["org.mockito:mockito-core"].
  • Kotlin compiler plugins, which jrs does not support.
  • A Shade <includes>, a <rawString> relocation or a wildcard jrs cannot match; the Gradle proguard { } task's keep rules.
  • A fork count worked out from the machine's cores.

An explicit standard-library dependency (kotlin-stdlib and friends) is dropped, since jrs implies it.

Troubleshooting

No JDK found, or the wrong one

Set JAVA_HOME to a JDK 17 or newer, or put its bin/ on PATH. For a pinned version, the error lists the versions jrs did find; add the missing one to [jdks] in the user configuration. jrs -v build names the JDK in use.

Lombok or another processor does nothing

On JDK 23 and later, add -proc:full to java.javac-args, and make sure the processor is a compile-only dependency. See Annotation processors.

Mockito warns about a dynamically loaded agent

Add test.java-agents = ["org.mockito:mockito-core"], as Mockito 5 on JDK 21+ asks.

"Main class not found" in a Kotlin project

A file-level main in Main.kt lives in class MainKt: set main-class = "com.example.MainKt".

A Kotlin Multiplatform library resolves to no classes

Declare its -jvm artifact instead, such as org.jetbrains.kotlinx:kotlinx-coroutines-core-jvm.

401 or 403 from a repository

Credentials are missing or wrong. They go in [credentials.<repo>] of the user configuration or in JRS_REPO_<NAME>_* variables, keyed by the repository's name in jrs.toml, never in the manifest.

A checksum mismatch

The repository served different bytes than jrs.lock pinned, or than its own .sha1. jrs refuses them on purpose. Find out why before running jrs update to accept new pins; jrs verify re-checks what is already in the cache. For a local jar you replaced deliberately, jrs update pins the new one.

An --offline build fails on a missing artifact

The cache lacks something the build needs. Run jrs fetch online first; it downloads the dependencies, compilers, task tools and test launcher.

A duplicate class in a fat jar

Two dependencies ship the same class; jrs names it and both jars. Drop one side with exclusions, or move one out of the way with [package.relocate].

A version range in a POM

jrs rejects Maven version ranges such as [1.0,2.0) with an error rather than guessing at one. It builds only against versions written down.

Garbled output in a log

Animation is off automatically when stderr is not a terminal or a CI variable is set. If a tool still captures escape codes, pass --progress never --color never, or set NO_COLOR=1.

Something else

Rerun with -v to see every command jrs runs, and check the issue tracker. An exit code of 101 is a bug in jrs; please report it.
