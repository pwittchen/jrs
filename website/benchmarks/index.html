Benchmarks

The build is done before the daemon answers.

jrs is one native binary that starts in milliseconds and keeps nothing running between builds. On the same projects, built the same way, it finishes a no-op build in about 60 ms, five times faster than a warm Gradle daemon and more than ten times faster than Maven. It is slower when a change forces a lot of compiling: an API change in a large project, or a clean build of several modules, where a warm Gradle daemon finishes up to four times sooner. Five ways to build the same project

Gradle is measured three ways: with a daemon kept warm from the warm-up runs, the same with the configuration cache, and with --no-daemon, which is what a CI job or the first command of the day sees.

Where jrs wins, and where it does not yet

Faster

  • Anything start-up bound. No-op builds in 63–85 ms on every project: 4–7× a warm Gradle daemon, 11–15× Maven, 26–37× Gradle without a daemon.
  • Edits that change no API. One source recompiled and nothing else run: 25–45% ahead of the daemon, 4–6× ahead of Maven.
  • Cold builds. 0.6–2.2 s with empty caches, against 1.4–3 s for Maven and 11–14 s for Gradle, which sets up its whole home first.
  • Fat jars of plain projects. 1.8–3× faster than shadowJar on a warm daemon.
  • Small test suites and test selection. jrs test runs only the tests a change reaches: 626 ms against 2.6 s for Maven in the workspace.
  • On CI. Against Maven and Gradle without a daemon, jrs is faster in every cell but three.

Gradle's daemon still wins

  • An API change in a big project. jrs recompiles everything that reaches the changed class; Gradle's analysis recompiles less, in a warm compiler. 1.84 s against 0.64 s on 2000 classes.
  • Workspaces. Members compile one after another, each in a fresh javac; on six members a clean build takes 1.98 s against the daemon's 0.79 s and Maven's 1.58 s. Building members in parallel is next on the roadmap.
  • Long compiles. At 2000 classes a hot, JIT-warmed javac overtakes a fresh one: 1.55 s against 1.26 s for a clean build.
  • Spring Boot's jar. 719 ms against bootJar's 513 ms; jrs unpacks every dependency into one jar where Boot nests them.

How it was measured

  1. The same build, three times. Each project has a jrs.toml, a pom.xml and a build.gradle.kts for the same sources, dependencies, --release, JUnit 5 tests and fat jar. The generated projects get all three from one description.
  2. Checked before timed. No project is timed until every tool resolves the same runtime classpath, runs the same tests with no failures, prints the same output and builds a jar that starts.
  3. No network, no build cache. Every tool reads one local mirror of Maven Central and the Gradle Plugin Portal; jrs, Maven and Gradle all run with their build caches off.
  4. Default configuration. No tuning flag jrs has no counterpart for. Output goes to a file, never a terminal. Runs go round-robin over the tools.
  5. The setup. jrs 0.11.0, Maven 3.9.16 and Gradle 9.1.0 on Corretto 25.0.2, the machine below, on 2026-10-14.

The rules, the scenarios and the harness are in specs/BENCHMARKS.md; the numbers and their reading in specs/BENCHMARKS_SUMMARY.md. Run it on your own machine: 

git clone https://github.com/pwittchen/jrs && cd jrs
JRS_BENCH_RECORD=1 cargo bench --bench compare   # fill the local mirror, once
cargo bench --bench compare                      # writes benchmarks/REPORT.md

Time it on your own project

jrs migrate writes a jrs.toml beside your pom.xml or Gradle build and leaves them in place, so the comparison costs one command. 

cd my-project
jrs migrate
time jrs build     # then once more, with nothing changed
