Why jrs

The same build, in a file you can read.

Maven and Gradle can build anything, and a single-module project pays for that: a wrapper, a DSL or a plugin block for every job, and a JVM that starts before any work is done. jrs covers a narrower set of projects and makes the safe choices the default ones.

One project, two builds

A Java 21 application with Guava, JUnit 5 tests and a runnable fat jar with a pinned, reproducible dependency graph. On the left, everything jrs needs. On the right, the Gradle build that does the same.

The last two blocks are the ones most Gradle builds leave out: without them there is no lockfile and the jar differs from build to build. In jrs they are not settings.

What you get without asking

Starting
jrs is one native binary with no daemon to keep warm. A JVM starts only for the work that needs one: javac, your tests and your application. Nothing stays running between builds.
Pinning
The first resolution writes jrs.lock with every version and checksum in the graph, the Kotlin, Scala and Groovy compilers included. Commit it and every machine builds the same graph. A released jar whose bytes change under the same version fails the build.
Reproducing
Jar entries are sorted, timestamped 1980-01-01 and given fixed permissions, so two builds of the same inputs produce byte-identical jars. Nothing to switch on.
Auditing
jrs.toml is data, and jrs has no plugins. Nothing a project or a dependency writes runs inside the build tool. Your own steps are tasks: commands run as subprocesses at fixed points, which can add to the build but never reorder it. Reviewing a build means reading two files.
Packaging
Plain, portable and fat jars, with META-INF/services and Spring's registries merged instead of overwritten. jlink runtimes, jpackage installers, GraalVM native executables and ProGuard, each one flag of jrs package instead of one plugin each.
Mixing
Kotlin, Scala or Groovy beside Java, calling each other both ways. Each compiler is fetched from Maven Central, pinned and run on your JDK, in a graph of its own that never mediates against your dependencies.
Migrating
jrs migrate writes a jrs.toml from a pom.xml or a Gradle build, Spring Boot included, and lists what it could not carry over. Your Maven or Gradle build stays in place until you delete it.

Who it fits

Single-module services

A Spring Boot or Ktor service in its own repository. The Spring Boot BOM goes in [managed], and the fat jar starts with java -jar, no BOOT-INF/ layout needed.

Command-line tools

A fast build tool for small programs. --jlink ships a trimmed runtime, --native-image a single executable, --jpackage a .dmg, .deb or .msi.

Teams new to the JVM

Teams working mostly in Rust, Go or TypeScript, with a Java or Kotlin service or two. If you know Cargo.toml and Cargo.lock, you already know jrs.toml and jrs.lock.

Supply-chain requirements

Every released artifact pinned by checksum, reproducible output, --offline builds from the cache alone, and a build definition with no code in it to review.

Coding agents

A manifest an agent edits with jrs add and jrs remove, plain output with --progress never, the project model as JSON from jrs metadata, and a short edit, build and test loop.

First projects

jrs init scaffolds a main class and its test. The step from a single Java file to a project with dependencies and tests, without learning a build DSL first.

When to stay with Maven or Gradle

jrs is experimental and deliberately narrow. These are the cases it does not cover today; the roadmap says which of them may change.

  • Multi-module builds. One jrs.toml is one module. There is no reactor and no composite build.
  • Libraries you publish. jrs builds sources and Javadoc jars but does not sign or deploy to a repository.
  • Android. Out of scope, as is Kotlin Multiplatform beyond the JVM target.
  • Build plugins you depend on. kapt and KSP, an annotation-processor path, JPMS modules, TestNG and container images from the build are not supported.
  • IDE import. IntelliJ IDEA does not import a jrs project yet. The plugin is planned; jrs metadata is the model it will read.
  • A shared build cache. jrs recompiles only what changed, but does not share compiled outputs across machines the way Gradle's remote cache does.

Try it on your own project

jrs migrate only adds files, so trying jrs beside an existing build costs nothing. If something does not build, an issue with the project is the most useful report there is. 

cd my-project       # next to pom.xml or build.gradle(.kts)
jrs migrate         # writes jrs.toml and a report of what to review
jrs test
jrs package --fat

Timings against Maven and Gradle on the same projects are on the roadmap. This page will link to the report once it is published, including the cases where jrs is slower.
